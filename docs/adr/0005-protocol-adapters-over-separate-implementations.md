# 5. Protocol Adapters Over Separate Implementations

Date: 2026-08-06

## Status

Accepted

## Context

CloudVitta serves price comparisons across multiple protocol surfaces: REST (for web applications and curl), gRPC (for high-performance microservices), MCP (for Model Context Protocol AI tools), and A2A.

If each protocol transport implements its own validation, caching orchestration, and matching logic, the system risks business logic divergence and high maintenance costs. We must ensure that core business logic in the calculator engine remains decoupled from the transport layer serving it.

## Decision

We use **Protocol Adapters over a Single Core Engine** with strict one-way package dependencies and a centralized domain error interface:
1. **Single Core Engine**: All pricing calculations, attribute matching, and cache coordination reside in `internal/service`. Services accept and return protocol-agnostic Go domain types defined in `internal/domain`.
2. **Thin Transport Adapters**: Transport packages (`internal/transport/rest`, `internal/transport/grpc`, `internal/transport/mcp`) function strictly as thin adapters. They deserialize protocol requests, invoke `internal/service`, and serialize domain responses into protocol-specific payloads.
3. **Strict One-Way Imports**: `internal/service` never imports `net/http`, `google.golang.org/grpc`, or transport-specific packages.
4. **Domain Error Mapping**: `internal/domain` defines typed domain sentinel errors and categories. Transport adapters map domain errors mechanically to protocol-specific status codes (e.g., HTTP 400 with RFC 7807 problem details versus gRPC `codes.InvalidArgument`).

## Consequences

### Positive
- Bug fixes and pricing logic updates in `internal/service` take effect across REST, gRPC, and MCP simultaneously.
- Core business logic is straightforward to test in isolation without mocking HTTP requests or gRPC streams.
- Error handling is typed and deterministic across all protocol boundaries.

### Negative
- Maintainers must strictly prevent transport concerns (such as HTTP header extraction) from leaking into `internal/service`.
- Adding new error categories requires updating the transport mappers in each transport package.

## Alternatives Considered

### Alternative 1: Independent Business Logic per Protocol Transport
Rejected. Writing independent calculation and matching logic per protocol causes logic drift, creates inconsistent pricing sums across surfaces, and triples test maintenance costs.

### Alternative 2: Autogenerated gRPC-Gateway Proxy for REST
Rejected. Autogenerated gRPC-Gateway proxies prevent the emission of native RFC 7807 Problem Details error envelopes and limit fine-grained HTTP parameter validation and cookie handling.

### Alternative 3: Monolithic Handlers with Embedded Business Rules
Rejected. Embedding matching and pricing arithmetic inside HTTP handlers tightly couples domain rules to HTTP abstractions and prevents code reuse in gRPC and MCP servers.
